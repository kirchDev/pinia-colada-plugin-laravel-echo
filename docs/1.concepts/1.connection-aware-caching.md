# Connection-aware caching

A cache decides for itself when its data is old enough to fetch again. Pinia Colada expresses that as `staleTime`: a query that refetches on mount or on focus is a query that assumes nothing else is keeping it current.

Feeding a query from broadcasts changes that assumption — and quietly makes it conditional. While the socket is up, events keep the entry current and polling is waste. While it is down, nothing is keeping it current, and the entry is exactly as stale as an ordinary query would be. The condition is the connection, and the connection is not something the cache can see.

## The failure this prevents

A socket does not usually announce that it broke. A tunnel, standby, a wifi handover — the connection drops and the client stops receiving events. Nothing throws, no request fails, and the cache entry keeps its `success` state and its last timestamp. It looks fresh. It is not.

The visible form of that is a counter that stopped being true: a notification badge showing three unread when there are eleven, with nothing anywhere reporting the gap. It resolves itself when something else happens to trigger a refetch, which may be never.

That is the failure worth designing against, because it is silent on every side. A subscription that never opens is noticed in a minute; a subscription that stops delivering is not noticed at all.

## The rule

Echo's connector reports the connection's state and lets a caller subscribe to its changes. The plugin reduces that to two facts — connected, or not — and derives everything from the transitions between them:

- **Becoming connected** relaxes staleness to the query's `echo.staleTime`, where it declared one. That is the query saying "events cover me now".
- **Becoming disconnected** puts the query's own `staleTime` back. Normal refetch behaviour resumes, because from that moment it is the only thing keeping the data current.
- **Becoming connected _again_** additionally invalidates the entry once, to pick up whatever arrived while nobody was listening.

The first connection is deliberately not a reconnect. The entry has just been created and fetched; invalidating it there would refetch data that is one round trip old.

## Why it is built this way

**Relaxing staleness is opt-in, invalidating on reconnect is not.** The two differ in what happens when someone is wrong about them. A reconnect invalidation that was not needed costs one request; a query whose refetching was silently switched off, and whose events then stop, is the failure above with an extra step. So the risky half requires a deliberate `echo.staleTime`, and adding `echo` to an existing query cannot change how it refetches.

**Two states, not five.** The connector distinguishes connecting from reconnecting from failed. Every one of those means the same thing to a cache — no events are arriving — and collapsing them is what makes "invalidate exactly once" true rather than approximately true: a drop that recovers through several intermediate states is still one transition back to connected.

**The rule is global, the opt-in is per query.** There is one connection, so its turns are one event; what each entry does about it is read from that entry's own options. That is what lets one query relax to `Infinity` while another beside it keeps refetching every thirty seconds on the same socket.
