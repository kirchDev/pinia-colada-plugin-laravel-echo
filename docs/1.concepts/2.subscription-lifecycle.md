# Subscription lifecycle

A subscription has to end. The question is what decides when — and the answer the plugin picks is the cache entry, not the component.

Colada's cache exposes its own actions to plugins. Two of them bracket an entry's life: one fires when an entry is created and first extended, the other when it is removed. Subscribing on the first and leaving on the second ties the channel to the thing whose data the events are for, which is the entry — not to whichever component happened to mount first.

## Why not a composable

A composable is the obvious shape for this, and it is the wrong one for two reasons.

**The subscription would follow the component, not the data.** Two components reading the same query would open two subscriptions to the same channel; one unmounting would tear down a subscription the other still needs, or leave a second one running. The cache already solves that problem for the query — the entry is shared, the fetch is deduplicated — and a subscription hung off components does not inherit any of it.

**A plugin has no component lifecycle to hang from.** Echo's Vue bindings are composables: they bind to `onUnmounted` and only run inside a component's setup. A Colada plugin runs once, at install time, with no component anywhere near it. That is not an inconvenience to work around — it is the same fact as the first reason, seen from the other side.

## Channels are reference-counted

Nothing stops two entries from naming the same channel; a list and its unread count are the obvious pair. So a channel is opened once, and each entry that names it holds a count on it. Removing one entry stops that entry's own listeners and drops the count. The channel is left only when the count reaches zero.

Leaving eagerly instead — the moment the first entry goes — would silently deafen every other query on that channel. It is the same class of failure as a dropped connection: nothing throws, and the symptom is data that stops updating.

## The options object is rebuilt on every render

This is the mechanic most likely to surprise someone changing the code. Ensuring an entry does not mutate its existing options — it builds a **fresh** options object and assigns it. A value written directly onto an entry's options therefore survives exactly until the next render.

That matters for the relaxed `staleTime` from [connection-aware caching](1.connection-aware-caching.md), which is written onto the entry's options and would otherwise be quietly dropped. The plugin handles it by also observing the ensure action and re-applying, and by remembering the **identity** of the object it patched along with the value that object held first. Holding the identity, rather than just the number, is what makes restoring safe: when the object has been replaced, there is nothing of the plugin's on it to undo, and the query's own value is already in place.

## What the handler is given

A handler receives what Echo delivered and a context bound to its entry — the event name, the entry's key, the entry, the cache, and handles for reading, writing and invalidating that entry's data.

It gets no interpretation of the payload, deliberately. How a row is prepended, replaced, merged or counted is a property of the application's data, not of the transport, and a plugin that guessed would be useless to the second consumer. The context's job is to remove the boilerplate around the decision, not to make it.

The context's typing is a decision in its own right — see [ADR-0003](../99.adr/0003-keep-the-event-context-free-of-the-query-data-type.md).
