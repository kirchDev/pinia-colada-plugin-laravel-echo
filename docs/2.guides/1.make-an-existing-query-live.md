# Make an existing query live

You have a `useQuery` that works. You want it fed by broadcasts too. The plugin is installed. This is the order to do it in, and the two things that are easy to get wrong.

The README's option table is the reference for what each key accepts; this page is about the decisions around them.

## Steps

1. **Check the key covers whatever the channel name depends on.** The channel is resolved once, when the cache entry is created, so a name derived from something the key does not mention produces an entry still listening on the old channel after that something changes.

   ```ts
   // The channel names the user, so the key has to as well.
   key: () => ['notifications', 'list', userId.value],
   echo: { channel: () => `App.Models.User.${userId.value}`, /* … */ }
   ```

   This is the single most common mistake, and it fails silently: the query refetches correctly and the events simply stop arriving.

2. **Add the listeners, and nothing else yet.** Leave staleness alone on the first pass, so you can tell broadcast handling apart from refetch behaviour if something is off.

   ```ts
   echo: {
     channel: () => `App.Models.User.${userId.value}`,
     listen: {
       '.NotificationBroadcasted': (payload, { setQueryData }) =>
         setQueryData<Notification[]>((old) => [payload, ...(old ?? [])])
     }
   }
   ```

   The visibility defaults to `private`, which is what a user-scoped channel wants. Pass `visibility` for the other three. Write the channel name **without** its prefix — `private-` and friends are Echo's to add.

3. **Give the handler a type argument.** `setQueryData` and `getQueryData` do not inherit the query's data type, on purpose ([ADR-0003](../99.adr/0003-keep-the-event-context-free-of-the-query-data-type.md)). Name it at the call, as above, or the updater's previous value arrives as `unknown`.

4. **Decide whether events should relax staleness.** Only now, and only if you can answer yes to: do the listeners cover _every_ way this data changes? If a mutation elsewhere in the app can change it without a broadcast, the answer is no and you are done — leave `echo.staleTime` unset.

   ```ts
   staleTime: 30_000,                        // whenever the socket is down
   echo: {
     staleTime: Number.POSITIVE_INFINITY,    // while it is up
     // …
   }
   ```

   The query's own value is what applies while disconnected, so keep it sensible rather than deleting it.

5. **Verify a reconnect.** Kill the connection (offline in devtools is enough), let a broadcast happen without you, and restore it. The entry should invalidate once and refetch, and the missed data should appear. That path is the reason the plugin exists, and it is the one that never gets exercised by accident.

## Checklist

- [ ] The query key names everything the channel name is built from.
- [ ] The channel name carries no visibility prefix, and `visibility` is set where it is not private.
- [ ] Each handler passes a type argument to `setQueryData` / `getQueryData`.
- [ ] `echo.staleTime` is set only where broadcasts cover every change to the data.
- [ ] The query's own `staleTime` is still a value you would want while offline.
- [ ] A drop-and-restore of the connection ends with the entry refetched once, not zero or twice.
